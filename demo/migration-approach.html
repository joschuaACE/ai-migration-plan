This makes it reusable across DATEV's entire legacy portfolio without rebuilding the tooling each time.

Process Overview

The migration follows a strict phase-based workflow. Each module passes through the same sequence of activities, with automated quality gates between phases. The process is deterministic, resumable, and produces traceable artifacts at every step.

End-to-End Flow

Init → Detect → Map → Analyze → Plan → Execute → Verify → Review

Initialization (Init → Detect → Map) runs once per project. The module cycle (Analyze → Plan → Execute → Verify → Review) repeats for each module in the dependency-ordered roadmap. Session interruptions are handled by the Resume capability, which reads persistent state and re-enters at the correct point.

Two Modes of Operation

Mode When What Happens
One-time setup Project kickoff Scan source, build knowledge graphs, detect technologies, generate roadmap, create target skeleton
Per-module cycle Each module in roadmap Deep analysis → wave-ordered plans → parallel execution → multi-dimensional verification → two-pass review

Phase Details (Condensed)

Each phase has a clear purpose, defined inputs, and measurable outputs. Quality gates block progression until met.

Phase Purpose Key Outputs Quality Gate

Execution Phase — Wave Strategy Detail

Waves follow target architecture dependency direction (inside-out):

domain/model → domain/port → domain/service → application → adapters-out → adapters-in

Plans within the same wave execute in parallel (no inter-dependencies within a wave). Each wave must pass compilation + tests + architecture rules before the next wave starts. Failed gates trigger a fixer agent (max 2 attempts) before escalating to a human.

Architectural Decisions — Reasoning

Every architectural choice in this framework exists for a specific, defensible reason. This section explains the why behind each major decision.

Decision What We Chose Why (Reasoning) Alternatives Considered
Target Architecture Hexagonal (Ports & Adapters) Enforces domain purity automatically via architecture tests. Domain layer has zero framework imports — testable without infrastructure. Dependencies always point inward. Layered (too permissive), Clean Architecture (same idea, different naming), Vertical Slices (harder to enforce automatically)
Translation Strategy Hybrid: conservative for business logic, modern for infrastructure Business logic must be behaviorally equivalent (conservative minimizes risk). Infrastructure code benefits from modern idioms (records, sealed types, virtual threads). Pure 1:1 (produces non-idiomatic code), Full rewrite (loses behavioral guarantees)
Quality Enforcement Automated gates (compile-time, not review-time) Review comments get ignored under schedule pressure. Compilation failures cannot be ignored. Architecture violations are build failures, not suggestions. Code review only (unreliable), Linting (warnings get suppressed)
Execution Model Wave-based parallel with blocking gates Waves respect dependency ordering (inner layers first). Parallelism within a wave maximizes throughput. Blocking gates prevent error propagation across waves. Sequential file-by-file (too slow), Full parallel (dependency violations)
State Management Flat markdown files in .migration/ directory Human-readable without tooling. Version-controlled alongside code. Survives agent crashes — any agent can resume from state files. No database dependency. Database (requires infrastructure), JSON (less readable), External service (single point of failure)
Agent Architecture Specialized sub-agents per task Different tasks need different capabilities: scanners need speed, analyzers need depth, translators need precision. Specialized agents outperform generalists on each task. Single agent (context limits, no parallelism), Human-only (doesn't scale)
Documentation Generated ARC42 from migration artifacts Documentation that requires separate effort drifts from reality. By generating from actual analysis artifacts and knowledge graphs, docs are always current. Zero extra work. Manual ARC42 (2-4 weeks, instantly outdated), No docs (compliance failure)

Knowledge Graph — Selection & Role

Why a Knowledge Graph?

Legacy codebases are too large and too interconnected for sequential file-by-file analysis. A knowledge graph provides:

  • Structural understanding at scale — relationships between 500+ files visualized and queryable
  • Community detection — automatically identifies logical module boundaries in flat directory structures
  • Quantitative drift measurement — source↔target graph comparison produces numerical metrics, not subjective opinions
  • Dependency ordering — graph traversal determines which modules must migrate first
  • Architecture documentation — ARC42 sections generated directly from graph data

Two Complementary Tools

Tool Role Why Selected Integration Points
Graphify Analytical backbone Leiden algorithm for community detection. Edge confidence tiers. Hidden dependency discovery. Works without LLM token cost (AST-based). Init (source graph), Execute (target graph), Verify (comparison), Review (ARC42)
Understand Anything Human interface & domain extraction Interactive dashboard for presentations. Business domain extraction (meaningful module names). Onboarding guides. Diff impact analysis. Init (source understanding), on-demand throughout project

How They Work Together

Graphify answers: "What depends on what? Where are the coupling hotspots? How much has the architecture drifted?"

Understand Anything answers: "What does this code do in business terms? How should modules be named? What's the recommended migration order for a human audience?"

Together: Graphify provides the quantitative foundation; UA provides the human-readable interpretation. Disagreements between them signal architectural concerns that need human attention.

Target Architecture (Hexagonal)

Layer Contains Allowed Dependencies Enforcement
Domain Entities, value objects, domain services, port interfaces Language standard library only ArchUnit: zero framework imports
Application Use cases, DTOs, mappers Domain layer, transaction management Cannot import adapter packages
Adapter IN Controllers, CLI commands, message listeners Domain ports (in), Application DTOs Cannot access domain implementations
Adapter OUT Repository impls, HTTP clients, file I/O Domain ports (out), persistence frameworks Cannot access Adapter IN

Framework Compatibility Architecture

One Source, Multiple Agents

The knowledge base (standards, workflows, hooks) is maintained once in portable markdown. Agent-specific installers format this content for each platform's native conventions:

Agent Configuration Mechanism Status
GitHub Copilot .github/copilot-instructions.md + workspace rules + custom instructions Target
Kiro .kiro/steering/ + .kiro/skills/ + .kiro/hooks/ POC Proven
Claude Code CLAUDE.md + .claude/settings.json POC Proven

Adding a new agent requires only a new installer script (~100 lines) that reads docs/ and formats it for the agent's conventions. The methodology content stays unchanged.

Drag-and-Drop Installation

Installing the framework into any project takes one command. The installer reads the portable knowledge base, detects which agent to configure, and writes the appropriate files to the target project. No manual configuration required.

How It Works

  1. Clone the framework repository
    git clone <repo> migration-framework
  2. Run the interactive installer
    cd migration-framework && ./install.sh
    Asks: Which agent? Where is your project? What output type?
  3. Framework writes configuration to your project
    Standards → steering files. Skills → workflow commands. Hooks → quality automation. All in your repo.
  4. Start migrating
    /migrate-init ./src (Kiro) or "run migrate-init on ./src" (Copilot/Claude)

Key Point: Non-Invasive

The installer adds configuration files only. It does not modify your source code, build system, or existing project structure. The framework lives alongside your code. Uninstalling = delete the generated config directory.

Interruption Recovery, Checkpoints & Execution Environment

How the Framework Handles Interruptions

AI agents have limited context windows and sessions can be interrupted at any time (network failures, token limits, user pauses). The framework is designed to survive any interruption without data loss.

Mechanism How It Works Recovery Time
Persistent state file .migration/state.md updated after every significant action — records current phase, module, wave, and completion % Instant — agent reads state and continues
Git checkpoints Atomic commit per completed plan. Each wave is a checkpoint. Phase completion = git tag. Zero-loss — code is committed before advancing
Stall detection If no progress for 10 minutes, state file is marked "stalled" with last-known position Resume reads stall marker and re-enters at correct point
Context compaction When agent context window fills, migrate-resume reads all .migration/ artifacts to rebuild understanding 2-3 minutes (reads state + recent plan + last output)

The Resume Workflow

Interruption → Read state.md → Identify position → Load context → Continue execution
Execution Environment

The framework runs in the developer's local environment:

  • No cloud infrastructure required — everything runs locally (IDE + terminal + git)
  • No database — state is flat markdown files in .migration/
  • No external services — only the AI agent's API (Copilot, Kiro, Claude, etc.)
  • Fully offline-capable for state management — only translation requires API access
  • Works in air-gapped environments if the AI agent supports local models

Checkpoint Granularity

Level What's Saved Recovery Granularity
Per-plan (finest) Git commit with translated file + test Resume from exact plan that was interrupted
Per-wave All plans in wave committed; gate results recorded Skip completed waves, start next wave
Per-phase Git tag + state.md updated Entire phase can be re-run if needed
Per-module Module tagged complete in VCS Module is done — advance to next in roadmap

Backup: Compliance & Data Policies

Data Handling During Migration

Concern How the Framework Addresses It
Source code exposure to AI Source code is sent to the configured AI agent's API only. No third-party services. No telemetry. Agent choice determines data residency (e.g., GitHub Enterprise = EU data centers).
Secrets in source Framework scans for potential secrets during Init phase. Flagged files are excluded from AI processing and require human handling.
Audit trail integrity All artifacts in .migration/ are git-committed. Tamper-evident via git SHA history. Complete chain: what changed → why → verification → approval.
Reproducibility Every phase can be re-run from its inputs. Git tags mark known-good states. Plans are deterministic specifications — not stochastic prompts.
Intellectual property Migrated code is committed to your repository. No code leaves your infrastructure beyond AI API calls. Framework itself is portable markdown — no cloud dependency.

Compliance Alignment

Standard Relevant Controls Framework Support
ISO 27001 A.12 Operations Security, A.14 System Development Automated quality gates, access control via git, audit trail
GDPR (if applicable) Data minimization, purpose limitation Only source code processed; no PII handling; agent choice controls data residency
BSI IT-Grundschutz APP.1 (Application Development) Documented architecture decisions, enforced coding standards, test evidence
DATEV Internal Policies AI usage guidelines, code review requirements Human-in-the-loop at all decision points; two-pass review; explicit approval before execution

DATEV-specific AI usage policies should be reviewed with the compliance team to confirm which AI agents are approved for processing internal source code. The framework supports any agent — the compliance team selects which one.

Backup: Security Considerations

Attack Surface Risk Mitigation
AI hallucination in translated code Medium — AI may introduce subtle logic changes Multi-dimensional verification (semantic + architecture + graph-based). Two-pass review. Behavioral equivalence scoring blocks modules below threshold.
Supply chain (dependencies) Low — Migration Ladder minimizes new dependencies Iron Law #3: "No new dependency without checking if the platform already provides it." Every dependency requires explicit justification in decisions.md.
Injection via source code Low — AI reads source but doesn't execute it AI agents operate in sandboxed environments. Only Gradle build commands are executed. No arbitrary code execution paths.
Data exfiltration via AI API Depends on agent choice Agent selection determines data handling. GitHub Enterprise: no training on your code. Private deployment options available for all supported agents.
Tampering with migration state Low — state files are in git All .migration/ files are version-controlled. Unauthorized changes visible in git diff. Git hooks can enforce signed commits.

Security Architecture Enforcement

  • Domain purity — business logic layer has zero external dependencies (smallest attack surface possible)
  • Architecture tests as security gates — prevent accidental exposure of internal implementations through public APIs
  • Module-info.java — Java module system enforces encapsulation at the JVM level (not just convention)
  • No reflection — framework encourages constructor injection and explicit wiring over reflection-based magic
